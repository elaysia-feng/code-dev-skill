# TypeScript 前端规范

适用于 React、Vue、Next.js 等前端应用；npm 库的导出和发布另外加载 `typescript-package-guidelines.md`。不要把 npm 库规则套到普通页面项目。

## 目录与职责

目录结构见 [project-structure.md](project-structure.md) 的前端章节。先确认框架和路由机制：框架保留目录、入口、文件命名优先，不能为了统一目录破坏文件路由。既有结构调整遵循入口的迁移选择。

- 页面负责路由参数、布局和功能组合，不承载所有请求、转换与复杂业务流程。
- 业务专用组件、请求、类型、hooks/composables 优先与功能放在一起；真正跨功能共享后才移到全局目录。
- 通用组件只处理展示与交互，不直接绑定某个业务接口。简单页面无需先拆出完整功能目录。
- API 层负责网络请求与协议映射；业务判断留在所属功能。不要为一个请求建立多层纯转发包装。
- 区分组件局部状态、共享交互状态和服务端数据；不把所有状态放进全局 store，不为几次请求引入新状态框架。
- 类型放在所属功能或消费者旁边；仅稳定共享契约放到共享类型模块，不创建包揽所有类型的文件。

## 交互与边界

- 网络交互按实际场景处理加载、空结果、失败和重复提交；过期响应不能覆盖更新的状态，卸载后的订阅/副作用应释放。
- 前端校验用于交互体验；权限与业务约束仍由服务端执行。客户端代码不放服务端密钥。
- 使用已有请求、路由、状态和样式方案。服务端/客户端模块边界按框架要求处理，不把服务端依赖引入浏览器代码。
- 注释遵循 [code-comment-guidelines.md](code-comment-guidelines.md)：多阶段提交、上传、状态恢复等流程按真实层级编号；简单渲染、单步事件处理不机械补编号。

## 验证

运行项目已有的类型检查、lint 和构建；涉及用户交互时验证实际页面流程及相关失败状态。没有浏览器验证时如实说明，不用构建成功代替交互验证。
