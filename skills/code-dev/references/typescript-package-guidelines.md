# TypeScript npm Package Guidelines

## Scope

This guide covers creating, maintaining, or publishing TypeScript/JavaScript packages that other projects install, and its rules are mandatory. All other TypeScript code (application projects, frontend pages, internal modules) follows the general structure requirements in [`project-structure.md`](project-structure.md) and the Simplified Chinese comment requirements in [`code-comment-guidelines.md`](code-comment-guidelines.md).

## Package entry points and public API

- First confirm whether consumers use Node.js, a browser bundler, or both, and what ESM/CommonJS target the project currently uses.
- When creating a new Node.js package, use the package.json `exports` field to declare the public entry point and subpaths. `exports` hides every deep path that is not listed; before adding it to an existing package, check which import paths are already in use, keep a compatibility entry point, or treat it as a breaking change.
- Make `main`, `exports`, and `types` point at entry/declaration files that actually exist and are shipped in the package; `type` declares the module format for `.js` files. Every field must match the build output and the consumer target. Only add CommonJS/ESM dual output, compatibility entry points, or extra build tooling when the target runtime or the consumers genuinely need it.
- Public subpaths list only stable APIs; internal implementation does not need to be exported in full for the sake of "completeness".

A single-entry ESM package uses this configuration. `exports`, `types`, and `files` are always required, and the entry file must be generated by the project build pipeline and published with the package:

```json
{
  "name": "@scope/package",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./dist/index.js"
  },
  "types": "./dist/index.d.ts",
  "files": ["dist"]
}
```

## Type declarations

- A package aimed at TypeScript consumers must ship resolvable declaration files. Generate the `.d.ts` files with the existing build chain and make sure they are included in the published content.
- Point the package.json `types` field at the main entry declaration file; when there are multiple export entries, make every entry resolve to a matching declaration following the TypeScript/Node resolution the project supports.
- When declaration files depend on types from another package, put the declaration dependencies that consumers need in `dependencies` or `peerDependencies`, not only in `devDependencies`.
- Use `typesVersions` only when you genuinely need different declarations for different TypeScript versions.

## Published content and checks

- Use the package.json `files` allowlist to control the tarball content, including runtime artifacts, declaration files, required metadata, README, and the license; never ship tests, temporary build output, private configuration, or development-environment files.
- Before publishing, run `npm pack --dry-run --json` and inspect the actual list of files that will be published; verify especially that the entry points, declaration files, assets, and subpath targets all exist.
- If you add `exports` to an existing package, or remove a public subpath, evaluate version compatibility as a consumer-visible API change.
